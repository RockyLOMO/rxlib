# rxlib RSS Transport Profiles · 最终策略修订（统一 zlib 3、按需恢复内存）

> 基线：[`RockyLOMO/rxlib master 7a46f427`](https://github.com/RockyLOMO/rxlib/commit/7a46f427729c1c94833f0044826f2877a0e687d5)，2026-11-24 复查。
> 服务端预算：1 vCPU、768 MiB 整机内存。全局原则：正常业务交付与安全是底线；省流量第一、CPU 效率第二，允许用有界内存换取省流或性能。daily/game/weak 的 TCP 默认均启用 zlib 3（保留原有安全与已加密端口旁路）；game 以业务延迟为例外首要目标，并与 weak 一样允许按需用内存换取恢复能力；weak 在单核 768 MiB 预算下尽量接近 kcptun 弱网体验，在满足稳定性目标的候选中优先选择真实双向流量最低的策略。
> 本文是设计建议及源码静态 Review；参数为待验证初值，未实施、未运行基准测试。

## 1. Profile 定义

保留 `plain` 默认行为及兼容性；增加 `game` 和 `weak`，不使用较长的 `weak-network` 名称。三个业务 profile 共享编码、认证、缓存、调度和反馈机制，避免重复维护三套协议。

| 项目 | plain | daily（日常） | game（游戏） | weak（弱网） |
| --- | --- | --- | --- | --- |
| 第一目标 | 最低协议处理开销 | 最低实际双向流量 | 最低 P95/P99 延迟、卡顿 | 省流前提下尽可能接近 kcptun 的弱网体验 |
| 第二目标 | 兼容 | CPU 效率 | 控制资源、流量 | CPU 效率与资源上限；网络恢复后自动省流 |
| TCP 压缩 | 关闭 | zlib 3 | zlib 3 | zlib 3 |
| 恢复内存策略 | 不新增恢复缓存 | 现有有界缓存 | 按需扩大发送/乱序/去重窗口，优先低延迟 | 按需扩大发送/乱序/FEC 缓存及恢复窗口 |
| TCP FEC | 关闭 | 自适应 XOR | 自适应 XOR + 更及时修复 | 自适应 XOR / 可选 RS + 选择性修复 + TCP 兜底 |
| UDP FEC | 关闭 | 自适应 XOR | 默认关闭 | 自适应 XOR / 可选 RS，不默认可靠重传 |
| UDP 多倍发包 | 关闭 | 关闭 | 自适应 1～3 倍 | 默认关闭 |
| UDP 压缩 | 关闭 | 保留现状（默认关闭，可启用 LZ4 fast） | 默认关闭；有明确收益时选配 | 可选 LZ4 fast，保留低收益旁路 |
| UDP 跳跃 | 原有行为 | 保留现状 | 沿用已协商能力 | 保留现状 |
| 认证/加密 | 现有端口策略 | 同左 | 同左 | 同左 |

说明：TCP/FEC 是 RSS 的 UDP 快路径 + TCP 可靠修复，不等于给普通 TCP 直接增加 XOR。普通 UDP 没有可靠重传保证。不得让游戏 UDP 同时默认开启 FEC 和多倍发送，否则形成双重冗余。外部协议、直连、外部固定隧道维持既有语义。

## 2. daily：以真实总流量为目标

- 保留当前 XOR 自适应：关闭 / 16:1 / 8:1 / 4:1，连续 3 个干净窗口关闭校验，反馈超时降级；原始数据始终立即发送。维持 `parityCredit` 预算与 15～180ms 动态 flush。
- 低 PPS 不强制 100% FEC 覆盖；现有仓库测试中 20 PPS、16:1 的覆盖率 25%，这是可接受的预算取舍。优先优化不发 parity 的分组：提前判定可保护组，其他组走 DATA，减少无效 XOR、缓冲操作和 1B SHARD 头；必须保持冗余预算与保护覆盖率，不因包长/组长预测错误而恶化恢复。
- 优先修复重复流量：当 `AdaptiveStream` 可靠 TCP 接管所有待确认数据且尚未发送的本方向 parity 已无价值时，取消对应发送累积状态；不要清理接收端状态。修复超时需与实际 RTT/抖动及 FEC 到达机会协调，避免 FEC 和 TCP 同时做无效工作。
- 保留 512 序号位图、按需扩展 4→16 接收组及 300ms 过期；仅在测得缓存淘汰导致恢复率下降时扩容，并保持认证层窗口与交付窗口匹配。避免无界内存及 Netty direct buffer 泄漏。
- 不能仅凭 FEC 比例判断省流：统计压缩后实际数据、校验、重复补发、控制帧、协议头、探测及两方向 IP/传输开销。普通 UDP 不能以丢弃有效数据实现表面省流；比较相同有效负载及交付质量。

### 2.1 zlib 3 还是 6？

结论：daily、game、weak 默认统一启用 **zlib 3**；plain 保留原有默认关闭行为，已有端口安全策略和显式配置覆盖不变；允许在同一线格式下显式选择 1～9 中合适级别，重点测试 3/6，不默认升到 6。

当前 `RssSupport.TCP_COMPRESSION_LEVEL=3`，客户端和服务端创建 TCP 压缩编码器时使用配置级别。较高等级通常需要更多 CPU，压缩率增益随数据分布变化，不能预先承诺收益。1 vCPU 上多连接压缩可能造成 EventLoop 排队、超时及额外补发。

- 建议新增可选 `tcpCompressionLevel`（默认 3），只有压缩位开启才生效。zlib 的解码通常不要求对方采用同一压缩级别；两个发送方向各自可按预算选择级别，但客户端的配置不能假定会自动改变服务端编码器。若希望 per-user 双向指定，需经认证的策略协商或独立服务端配置。
- 对当前端口策略判定的已加密流量保持旁路（端口仅为策略提示）；保留现有安全约束，不自动打开敏感明文协议上秘密与攻击者可控内容共享压缩上下文的组合。
- 真实数据测试 zlib 1/3/6（必要时 9 仅供对照）：文本/API、游戏、已压缩文件、HTTPS、短连接、长期连接及并发混合。比较双方实际 IP 层字节、每 GiB 有效载荷 CPU 秒数、持续 CPU、GC、EventLoop 延迟和 P99。若 6 的增量省流明显且单核仍有余量，才升级指定用户/部署。
- 若需要建议验收门槛：6 相比 3 的真实总流量至少再降低 3%（仅初始实验门槛，可按成本调整），峰值负载下持续 CPU 建议留约 25%～30% 余量，P99 不明显恶化，不增加重传。不能以关闭安全功能获得收益。
- 保留 UDP LZ4 实现：现有最小 96B、至少节省 24B 且 12%、8 次低收益后旁路 30 秒。若未来默认启用，必须通过净流量实验；压缩发生于 FEC 之前，可能同时降低校验体积，具体取决于组内最大分片长度。

## 3. game：最先到达的副本立即交付

### 3.1 UDP 多倍发包

在不改变业务 UDP 协议的前提下，主动复制是低恢复延迟方案之一；不依赖后续包或 RTT，也不能降低原本的传播延迟。首包到达即交付，其余副本去重。单路径突发丢包、限速、拥塞时，副本相关性高，可能一同丢失，甚至扩大排队；故不能宣称一定是最快的技术。

建议参数（待测试）：

| 项目 | 建议 |
| --- | --- |
| 冷启动 | 2x 短时起步（例如首个有效反馈窗口），可配置 1x 省流 |
| 倍率范围 | 1～3，2x 为常用弱网档；不默认 4x/5x |
| 上调 | 有足够样本且发现实际方向丢包/超出交付延迟目标时，1→2；2→3 仅在改善明显且非拥塞时 |
| 下调 | 多个有效干净窗口后逐级下降；无数据或反馈丢失不当作零丢包 |
| 首包 | 立即发送，不人为等待 |
| 副本间隔 | 0μs 默认候选（最低人为等待、少定时器）；对照 200/500/1000μs 及 1～5ms 轻度分散；以实测选择，不假定亚毫秒调度准确 |
| 背压/拥塞 | 优先原包，限制或丢弃附加副本；有界发送队列、PPS/字节预算，不用多发解决拥塞 |
| 去重 | 每逻辑会话、每方向独立序号；端口跳跃不重置窗口；首份有效包交付一次 |

独立丢包模型下，p=10% 时，1x/2x/3x 的全丢概率分别 10%/1%/0.1%，相应复制载荷开销为 0%/100%/200%（不含头部）。现实突发模型必须另测。

### 3.2 P0：现有多倍发包反馈不能直接用于 game

`UdpRedundantEncoder` 已支持一次复制到 direct ByteBuf、`retainedDuplicate()` 多副本及可选延时；可复用发送能力，不需要重新写底层多发。

但 `UdpRedundantStats.adjustMultiplier()` 以 `1 - totalReceived / uniqueReceived / currentMultiplier` 估计丢包，存在三个设计限制：

1. `uniqueReceived` 不包括所有副本都丢失的逻辑包，故估计偏低；1x 时收到的包通常 total=unique，更无法由这个公式检测真正的原包缺失。
2. 本地发送倍率并非远端发送倍率，双向不对称或倍率切换时会把不同方向混淆（源码也注释了回程倍率可能不同）。
3. `UdpRedundantEncoder.write()` 在倍率为 1 时直接透传，不加 RDNT 头；相应 `UdpRedundantDecoder` 不会为这些包记录 RDNT 序号统计，可能导致倍率降至 1 后无法根据实际丢包自动升回 2。仅改阈值无法解决。

修复方向：game 协商后即使倍率 1，也必须具有可追踪的逻辑序号（优先复用 RSS 会话内序号，而非重复包两层头）；按方向统计接收端去重前实际线包数、唯一逻辑包、序号缺口和乱序；通过已认证反馈报告给对应发送端；使用发送端同一序号窗口的实际发送副本数作为分母。初期可优先复用 `UdpDailyFec` 的 32 包缺口反馈思想，额外记录倍率变化和实际发送数，避免独立方向相互污染。反馈有损、长期空闲、样本不足均设明确状态，不用缺样本推导零丢包。

外层认证/防重放与内层复制必须协调：每份副本具有共同逻辑数据 ID；若复用完全相同的已认证包，外层会拒绝后续副本，这是正确交付行为，但估计副本到达率需要合适的计数位置。若每份副本独立封装，则先认证，再逻辑去重。禁止未认证包影响返回地址和反馈。

### 3.3 游戏 TCP

- 复用 `AdaptiveStream` 的 XOR 快路径和 TCP 修复；不改原始游戏 socket。默认启用 zlib 3，与 daily/weak 一致；不得为了提高压缩率而人为积攒游戏小包，保留及时 flush，验证小包压缩、EventLoop 排队与 P99。仅在实际压测发现延迟或 CPU 瓶颈时允许显式覆盖，既有安全和已加密流量旁路不变。
- 首包立即发送，RTT/抖动驱动的修复，现有 80ms 最小修复候选保留为初始值；不要把 80ms 当最终恢复交付时长或固定值。测试 40～80ms gap 宽限及基于实测 RTT 的修复；弱网时仍保留 TCP 回退。
- 不对 TCP 数据默认多倍发包，不默认引入 RS 或复杂 KCP ARQ；如果连续丢包成为瓶颈，再测试针对性策略。尤其 WoW 3.3.5a 本身是 TCP 游戏，UDP 多倍发送主要作用于原生 UDP 游戏，并不会自动应用于 WoW 的 TCP 流。

### 3.4 game 恢复内存：用内存换低延迟

- TCP 快路径发送与乱序窗口以现有 64 帧为起点，和 weak 一样按实测需要采用 128/256 帧候选，双端协商并设全局字节上限；扩大窗口用于减少频繁 TCP 回退和保留修复数据，不增加人为等待。
- UDP 多倍发包仍是首份有效副本立即交付，不等待其他副本、不强制有序、不做过期包重传。可以扩大逻辑序号去重窗口（512/1024 位候选，按 PPS 与乱序距离验证），保留有限统计状态与待发副本引用；有必要时扩大缓冲以减少分配和误淘汰，但限制附加副本积压和过期延迟，原包优先。
- 复用 weak 的窗口/内存预算管理，不为 game 建另一套缓存框架。内存不能代替低延迟调度，也不能挤占整机 768 MiB 的安全余量；低流量、低 RTT 时不预分配满窗口。

## 4. weak：省流优先的轻量 kcptun 替代方案

### 4.1 目标、非目标及客观边界

`weak` 不等于固定高冗余，也不只是把 `daily` 的 FEC 档位上限调高。目标是在 1 vCPU / 768 MiB 整机限制内，改善高 RTT、随机丢包、突发丢包、抖动、双向不对称等条件下的 TCP 隧道体验，尽量接近同负载 kcptun。**选择策略时，先满足数据正确性、资源安全上限和约定的业务稳定性目标，再最小化真实双向传输字节；在流量相近时选 CPU 更低的方案。** 允许有价值的压缩、FEC 和内存开销，不默认永久高冗余。达不到目标时明确报告差距，不伪造“等同 KCP”的能力。

- kcptun 默认 RS 10:3（连续发包时约 30% 校验载荷，并非全链路固定 30%）；其接收侧 AutoTune 识别对端分片参数，不等于发送端按丢包自适应。KCP 本身有 ACK、快速/提前/超时重传、发送/接收窗口及可配置拥塞控制。
- rxlib 现有单 XOR 每组仅能修一个缺失数据包；已有 GAP 修复单个缺口，超时则将整个尚未累计确认的窗口发往 TCP。仅扩大 XOR 冗余无法解决所有突发丢包和 TCP 队头阻塞问题。
- 保留 RSS 的原有 TCP 可靠通道和 UDP 快路径。先增强反馈、选择性修复和 FEC，只有实际需要时才增加有限 UDP 快速重传；不引入完整 KCP 状态机、永久高倍发包或自研通用可靠 UDP 协议。
- kcptun 主要是 TCP 字节流隧道；原生 UDP 保持数据报语义，只做纠错与去重。普通 UDP 不承诺可靠、有序传输，也不默认等待重传（避免游戏/实时流收到过期数据）。UDP 被阻断时 TCP 业务可回退 TCP，普通 UDP 按原有会话策略处理，不承诺自动经 TCP 修复。

### 4.2 自适应 FEC：先用 XOR，再按收益选择双校验

| 网络状态 | 候选策略（待验证） | 原则 |
| --- | --- | --- |
| 健康、无丢包 | 0；保持低成本观测 | 不永久发校验 |
| 冷启动 | 0 或短时 16:1/8:1（可选） | 只在历史或实测收益支持时使用有限初始预算 |
| 轻度随机丢包 | XOR 16:1 / 8:1 | 6.25% / 12.5% 名义包数预算 |
| 持续随机丢包 | XOR 4:1 | 25% 名义预算；若不改善交付则降档 |
| 突发丢包 | 对照交织 XOR、RS 8:2 | RS 8:2 与 XOR 4:1 同为 25% 名义校验包比例，纠错分布与等待时间不同 |
| 严重丢包 | 可选 XOR 2:1 或 RS 4:2 | 50% 仅作为受限实验档，不默认永久启用 |
| 高 RTT、无损 | 增加适当等待/窗口，保持低或零 FEC | RTT 高不代表丢包，FEC 无法消除传播延迟 |
| 高 RTT 且丢包 | 优先评估 FEC 净收益和修复延迟 | 减少等待一次 RTT 的机会成本 |
| 排队/拥塞/限速 | 减少冗余、限制补发速率 | 保护原包，不盲目增加发送量 |

所有比例为固定满组的名义校验包数相对原包数，不能代表线速字节；变长包的校验长度、认证和 IP 头、短组、反向反馈都会影响真实流量。RS 8:2 可在同组任意两份擦除时恢复（至少收到 8/10 份有效分片），但 20 PPS 时填满 8 个原包需约 350ms（从首包至末包），可能超过当前 180ms flush 和 300ms 接收寿命；稀疏流不得强行等满长组。RS 不是总比 XOR 好：要同时测短组、校验等待、接收缓存、真实 CPU 和恢复率。

- 默认优先使用现有单 XOR；`weak` 首轮最高常规预算仍建议 25%，不是默认发送 25%。RS 8:2 属于同预算候选，只有突发丢包时效果、总流量和单核 CPU 压测均支持才启用。优先采用成熟实现与基准测试，不自行发明 RS 算法。保留单 XOR 快路径，RS 状态/系数/缓冲按需建立并复用。
- 交织 XOR 可以让相邻数据包落到不同组，抵抗某些突发损失，不需增加校验比例，但会延长校验等待和增加组状态；当前 `base = seq - index` 的分组协议依赖连续序号，不可直接将交织套进旧线格式。先做离线对照，若有收益再用协商后的新组标识；低 PPS 默认不交织。
- 预算独立于组长、PPS 和 flush。允许更灵活的短组，但仍以实际字节预算、保护覆盖及延迟为约束；不能因每个短组都发 parity 而悄悄增加开销。日常模式保留原算法，weak 的参数和新格式单独协商。
- 使用接收端的原始丢包、有效恢复、乱序、连续缺口、RTT 基线/波动、队列水位、反馈丢失情况决定档位；升降档有滞回和最小样本。先实现简单分档，不为单核引入高频复杂控制循环。长时间无反馈视为未知，限制额外冗余，不能直接当作链路恢复。
- 现有 `UdpDailyFec.observe()` 每 32 个序号反馈，留 8 包乱序余量，低 PPS 首次反馈较慢且可能被 5s 超时影响。weak 可测试“包数或活动超时”触发的有限反馈；不能空闲心跳泛滥。反馈双向独立，报告序号防旧，认证与防重放保持。

### 4.3 TCP 修复：从单缺口到选择性修复，再到有界 UDP 快重传

建议实施顺序如下（新能力只启用于显式协商的 weak，daily 仅复用无副作用优化）：

1. **修复重复开销（P1）**：统计 timeout、GAP、窗口满、FIN 等原因的修复载荷、协议字节和重复交付过滤；TCP 已可靠接管对应组时停止无价值的待发送校验。协调 FEC 等待、GAP 宽限、RTT/RTO，不机械把最短 80ms 改成固定 500ms，也不在已无恢复机会时无限等待。
2. **选择性确认/修复（P1）**：复用累计 ACK，在有多个缺口时发送一个有限 bitmap（例如 64 位，从 nextRx 开始标明已收到的乱序帧），合并反馈；只修复已证实缺失的帧，避免把已缓存在对端的帧再次发送。正常顺序流继续用紧凑累计 ACK，不为每包发独立 SACK。SACK 不能跳过未确认的数据、误释放仍需可靠保存的 ByteBuf；未收到累计 ACK 前保留必要发送状态。TCP 补发必须满足有序交付约束；如无法确认选择性补发安全则按现有可靠 drain 兜底。
3. **有限 UDP 快速重传（P2，必须由 A/B 决定）**：如果只靠 TCP repair 在高 RTT、TCP 自身丢包和 HoL 下仍显著落后 kcptun，可对明确缺口通过已认证 UDP 快路径最多重发一次（每逻辑帧/每修复轮有上限），优先早到副本直接交付；失败后按有界 RTO 走 TCP。单个缺口没有证据表明 UDP 更有利时，可直接 TCP 修复。保留 TCP 控制/最终兜底，不同时无条件两路复制，不对正常 UDP 数据报引入此机制。若控制反馈经 UDP 可避开 TCP HoL，需支持认证、去重、限频、丢反馈后累计确认/超时兜底；不能让 UDP 控制丢失造成永久挂起。
4. **重发身份和计数**：新 UDP repair 帧沿用同一逻辑流序号，外层使用新的认证/防重放序号；单独区分原始数据、FEC parity、repair，重传不得污染原始丢包窗口或自动重复进入 FEC 编码，收端按逻辑序号去重。保留同一已压缩编码字节流，重发不重新压缩、不重复加密同一 nonce。可靠 TCP/UDP 路径的业务字节完全一致。

上述第 2 步和第 3 步是缩小与 kcptun 体验差距的重点。先做选择性 TCP 修复并测量，不能假定 TCP 通道一定更快；高 RTT、有损且 TCP HoL 明显时，有界 UDP ARQ 才更值得投入。不要直接实现 KCP 的完整重传队列、定时器、拥塞状态机和多路复用。

### 4.4 窗口、缓存、单核与拥塞

当前 `AdaptiveStream` 发送/乱序窗口为 64 帧，最大 UDP 数据载荷约 1237B。若持续高吞吐和高 RTT 导致窗口常满，现有代码会 drain 到 TCP 并暂时关闭 UDP（探测间隔 2s），可能增加修复和切换；这不是一个严格的总吞吐上限，因为 TCP 可继续发送。以 150ms RTT 为例，64 帧的 UDP 在途业务容量约 77 KiB，对应约 4.2 Mbps 的粗略窗口/RTT 估算，尚未计确认节奏和协议开销。

- 先记录 `windowFull`、切换原因、队列和 ACK 时延；只在确实因高 RTT 和有效在途需求导致频繁回退时，考虑 game/weak 按需 64→128→256（初始候选），不得所有连接固定扩大。发送与接收窗口须协调、版本化并符合有序交付、环形槽位及序号回绕约束。
- 256×1250B 约 312.5 KiB/方向的满窗口载荷量；并发数会放大成本。按连接/进程设实际在途字节上限，含 Netty 堆外内存、socket buffers、JVM heap、线程栈及其他服务；空闲释放 payload，允许保留小型状态。内存增加需减少回退、重复计算或流量，不能造成 swap 或 OOM。
- 512 序号去重和认证窗口、4→16 FEC 组、300ms 寿命保持为现有基线；高 PPS、高 RTT 实测有必要时，整体协调扩大（交付/认证窗口、FEC group TTL 与新窗口）。不要只扩大内层导致外层提前丢弃，也不以延长缓存代替丢包恢复。
- 拥塞感知从简单信号开始：TCP/UDP 写队列、丢弃、RTT 相对最小值增长、持续发送 backlog、实际恢复/校验收益。高 RTT 绝对值不代表拥塞。冗余和重传有明确字节/PPS 限额、全局上限与原包优先级；超过预算或 CPU 排队明显时优先减无效冗余/降回 TCP，不通过增加发送量加剧拥塞。
- 现有 zlib 3、已加密流量旁路、UDP LZ4 的低收益熔断均保留。weak 不默认提高 zlib 级别（单核下的额外排队风险）；真实负载验证压缩 6 能显著净省流且 CPU/P99 可接受时才开放。不得关闭安全策略换性能。

### 4.5 kcptun 对标、预算与退出条件

| 项目 | kcptun（对照） | weak（目标） |
| --- | --- | --- |
| 基础传输 | KCP/UDP 可靠字节流 | UDP 快路径 + TCP 最终可靠兜底 |
| 纠错 | RS，默认 10:3，配置可改 | XOR 优先；必要时同预算 RS 8:2 |
| 重传 | 快速/提前/RTO 重传 | 累计 ACK + 选择性修复，可选一次 UDP 快重传 |
| 流量 | 依配置、负载、丢包及重传而定 | 自适应降档，按实际总字节优化 |
| CPU | RS/KCP/加密、实现优化共同决定 | 单核实测，不预先宣称低于 Go kcptun |
| UDP 被阻断 | 常规模式需要 UDP 可达 | TCP 业务继续 TCP，保留原生 UDP 语义 |

在相同业务有效交付、网络条件和并发下，以 kcptun 默认 10:3 和一个实测省流调优档（如 10:1 或 0:0，记录真实参数）为对照，不只挑高冗余默认配置。首轮可将 P99 业务交付延迟、最长卡顿不超过对照约 1.2 倍设为实验目标（非承诺/SLA，低时延样本可另设绝对容忍值）；在达标的候选中选择双向 L3 字节最低的策略。未达标逐项归因于 FEC、重传、TCP HoL、排队或链路不可用，报告 CPU、内存和流量差距，而非盲目升冗余。不同条件下分别比较，不以一个均值掩盖弱网长尾。现有仓库 20 PPS、5% 名义丢包的模拟：随机恢复 33/83，平均连续丢 3 个线包的模型恢复 1/63（反向反馈无损）；这是旧 daily 基线，不是 weak 或 kcptun 的实测结论。

## 5. 接入方案：最小修改，明确协商

建议配置示例（新增字段和 profile 属于设计，不是当前可用配置）：

```yaml
shadowUsers:
  - ssPort: 6898
    transport:
      profile: daily
      tcpCompressionLevel: 3
  - ssPort: 6899
    transport:
      profile: game
      tcpCompressionLevel: 3
  - ssPort: 6900
    transport:
      profile: weak
      tcpCompressionLevel: 3
```

- `RssTransport.valid()` 目前只接受 plain/daily，新增 `game`、`weak`。现有 `fec` 是 TCP/UDP 启用范围位掩码，`tcp`/`udp` 是压缩/加密位掩码，不是强度；保留显式覆盖（包括 0）。建议新增明确的内部 FEC policy 与 UDP redundancy policy，不把强度塞进旧位掩码。默认 daily 与现有完全兼容；game 默认 fec=2、tcp=1、udp=0，并另启 UDP RDNT；weak 默认 fec=3、tcp=1、udp=0，内部选择增强 FEC 策略；普通 UDP LZ4 保留可选。选择性修复、UDP repair、新分组格式和窗口大小需独立能力版本与双端上限，不塞入既有掩码。
- `RssClient.Routes` 的缓存目前按 mask + adaptive 或 UDP features 索引；新增策略、压缩级别必须成为缓存键，否则相同旧 mask 的用户会错误共享配置。
- `SocksAdaptiveHandshake` 现有 0x83 私有协商只表示支持 adaptive TCP，nonce 格式固定。不得擅自附加字节破坏旧端解析；使用显式新版本/能力协商将 profile 和约束可靠传给双方，或双方分别选择本地策略并协商线格式能力。旧端只支持旧行为时明确拒绝新能力或按已声明规则回退（不静默宣称 game/weak 已生效）。服务端对客户端参数设置资源上限。
- `SocksConfig`、UDP relay RPC/group、`UdpLeasePoolKey` 必须包含有效策略/能力；隔离不同 profile 的 UDP 会话和池，不允许不同协议复用同一 relay 状态。`DailyUdpWire` 当前 feature 仅 LZ4/AES/FEC（1/2/4），不要只加一个 RDNT bit 就假设能完成双端协商。复用 RDNT 编解码核心或设计共享会话封装，避免多重序号/头部、FEC+RDNT 叠加。game 跨端口必须共用逻辑去重状态。
- 热更新作用于新连接/新 UDP 会话，已建立连接保持原策略；安全端口规则、认证、密钥和旧 `plain` 语义不变。更新 `docs/rss-transport.md` 和 `docs/reference/net/udp.md`。

## 6. Review 结论与实施优先级

| 优先级 | 项目 |
| --- | --- |
| P0 | 保留 512 序号窗口、4→16 缓存、动态 flush、压缩及安全机制；不回滚前几轮正确性修复 |
| P0 | 修复 game 多倍发送倍率 1 无反馈、双方向统计混淆、全丢漏计；完成 capability 协商、池隔离及逻辑去重 |
| P1 | 建立三个 profile；daily 基线不变，game UDP 复用自适应 RDNT，weak 复用 XOR 并建立方向性反馈及字节预算 |
| P1 | 消除 TCP 接管后无效 parity、优化无保护短组 XOR；保留正确性及冗余预算 |
| P1 | 单核 768MiB 下实测 zlib 3/6；不默认升 6 |
| P1 | weak：选择性 ACK/修复，补齐双向字节、回退原因及 P99 指标，建立 kcptun 同负载 A/B 基线 |
| P1 | game/weak：共享有界恢复内存管理，按需扩大 TCP 在途/乱序窗口，game UDP 适当扩大去重窗口；不增加游戏交付等待 |
| P2 | weak：若 TCP HoL/修复成为瓶颈，验证一次有界 UDP 快重传；反馈与拥塞约束 |
| P2 | weak：若突发损失成为瓶颈，对照同预算 XOR 4:1 / RS 8:2 / 交织 XOR；按净流量、CPU 和 P99 决定启用 |
| P3 | 只有以上措施仍不能达标且用户接受额外资源成本时才考虑更复杂 ARQ；不默认重写 KCP |

## 7. 验收矩阵

在 Linux 1 vCPU/768 MiB 实际约束（含 JVM、direct memory、OS 和其他服务）下测试，报告并发数和总吞吐。可用 netem 双向注入损失、延迟和乱序，测试同业务相同负载；以实际双方向网卡/IP 字节比较，不把只统计 parity 当省流。

- 对照：plain、旧 daily、三种新 profile、kcptun 默认 10:3 以及省流调优档（记录 FEC、压缩、加密、KCP mode、窗口参数）。kcptun 主要用于 TCP 隧道的可比测试，不与原生 UDP 游戏多倍发包直接等价。
- 速率：20/50/100/200/300/1000 PPS，真实游戏短包、网页/文件及混合并发；RTT 20/80/150/300ms，抖动 0/10/50ms，随机损失 0/1/5/10/20%，连续丢 2/3/5 包，双向不对称、反馈丢失、限速、乱序、UDP 阻断、端口跳跃。
- 正确性：TCP 字节完整且有序；UDP 不重复、不篡改，不因切换倍率 1→2→3→1 或跳端口破坏交付；无越界缓存及引用计数泄漏。普通 UDP 不承诺全可靠。
- daily：在同有效交付及可接受延迟下真实总流量不高于旧 daily（正常网络无额外 parity）；减少无效 XOR、重复补发；压缩仍有效。
- game：在同负载弱网下，业务 P95/P99 交付延迟、最长卡顿及逻辑包丢失率优于无多倍发送的对照，且健康网络自动回到 1x（须验证能够再次升档）；受限链路不以牺牲原包换冗余。开启 zlib 3，测试 64/128/256 TCP 窗口及 UDP 去重容量的收益，验证不增加首包等待。
- weak：在相同有效交付/负载下，对照 daily 和 kcptun 两档，报告真实总字节、有效 goodput、业务 P95/P99、最大连续卡顿、CPU 秒/GiB、GC、回退原因/字节、FEC parity 字节及恢复数。测试 64/128/256 自适应窗口、选择性 TCP repair、有限 UDP repair、XOR/RS 各候选，分离增量收益；高 RTT 无丢包不盲目加冗余，突发损失与拥塞分别报告。先满足业务稳定性和硬件上限，再选择实际流量最低的候选；没有候选达标则说明差距。
- 硬件约束：持续 CPU 预留约 25%～30% 为初始验收建议，监控 EventLoop P99、GC、进程 RSS、direct buffer、fd/UDP 端口数量和整机内存；内存可放宽但不能导致 OOM 或 swap 抖动。不要为固定指标牺牲基本稳定性。
